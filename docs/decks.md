# Decks

A deck is an npm workspace under `decks/<name>/` built with
[Slidev](https://sli.dev). Every deck copied from `templates/deck` already has
the live-question components, the interactive layouts and the optional dev-time
sync wiring in place.

There are two ways to put a live question into a deck:

- **Interactive slide layouts** — set `layout: poll` (or `multi`, `ranking`, …)
  in a slide's frontmatter and the slide renders the live question itself. The
  presenter's slide change auto-activates it.
- **Markdown comment blocks** — write a `<!-- live-question … -->` YAML block
  anywhere in `slides.md`; it renders nothing, and the question is imported
  from the deck's build manifest at server startup.

Both paths land in the same question store and flow through the same queue. The
in-slide `<LiveQuestion />` component then renders whatever question is active.

## Deck structure

```text
decks/meetup/
├── slides.md              # the deck itself (frontmatter + slides)
├── package.json           # workspace name drives `npm run dev -w <name>`
├── components/            # live Vue components (<LiveJoin />, <PresenterPanel />, …)
├── composables/
│   ├── useLiveRoom.ts          # shared WebSocket client
│   └── useDeckSlideQuestion.ts # slide-scoped live state
├── layouts/               # markdown-authored interactive slides
├── plugins/deck-sync.ts   # optional Vite dev plugin (watch + sync)
├── scripts/sync-deck.mjs  # optional dev-time sync to a running backend
├── public/                # images referenced as /image.png
├── style.css              # deck-level styles
├── THEME.md               # how the interactive layouts are themed
└── global-top.vue         # global overlay (join hint, voting state)
```

## Frontmatter metadata

The first YAML frontmatter block drives both the deck and the landing page
generated by `npm run build`.

```yaml
---
theme: default
title: My talk
info: One-line description for the index page.
date: 2026-09-28
tags: [kubernetes, cloud-native]
---
```

| Key | Used by | Purpose |
| --- | --- | --- |
| `title` | landing page + Slidev | Deck title |
| `info` | landing page | One-line description |
| `date` | landing page | Sort key (newest first); `YYYY-MM-DD` |
| `tags` | landing page | List of topic chips |
| `theme` | Slidev | `default`, `seriph`, … |
| `features` | server seed | Optional per-deck feature flags (see below) |

The landing page generator (`scripts/build-index.mjs`) only reads `title`,
`info`, `date` and `tags`. Everything else is standard Slidev frontmatter.

### Per-deck feature flags

Add a `features` key to the first frontmatter block to disable parts of the
audience app for a deck's seeded event. The value is parsed into a canonical
subset of `live`, `qa`, `slides`, `feedback` and `leaderboard`; an unknown token
is ignored (with a warning), and the list is re-ordered canonically:

```yaml
---
title: My talk
features: live, qa, slides
---
```

`scripts/extract-questions.mjs` writes the parsed list into the deck's
`questions.json`, and at startup the server maps it onto the event's
`feature_live` / `feature_qa` / `feature_slides` / `feature_feedback` /
`feature_leaderboard` columns. When a flag is off the corresponding audience
tab is hidden and its panel is disabled. Omit `features` entirely to leave every
feature on. The flags are normally seeded from the deck; you can also patch them
per event through `PATCH /api/admin/events/{id}`.

### Slidev frontmatter options used by the bundled decks

```yaml
---
theme: default
title: "Dutch Kubernetes/Cloud Native Meetup"
info: Cloud Native Amsterdam meetup deck with live audience Q&A and polls.
date: 2026-09-28
tags: [kubernetes, cloud-native, cncf, live-questions]
routerMode: hash          # hash routing keeps deep links working on static hosts
transition: slide-left    # slide transition
mdc: true                 # MDC syntax (components/blocks in Markdown)
fonts:
  sans: Inter
  mono: JetBrains Mono
colorSchema: light
aspectRatio: 16/9
layout: center
class: "text-center bg-white relative"
---
```

See the [Slidev documentation](https://sli.dev/custom/) for the full
frontmatter reference.

## Live components

Every component shares one WebSocket per `(base, event)` pair through the
`useLiveRoom` composable, and reconnects automatically. If the backend is
unreachable they render the join card and wait, so the deck still works as a
static presentation.

| Component | Props | What it shows |
| --- | --- | --- |
| `<LiveJoin />` | `event`, `room`, `base`, `size`, `hint` | QR code + short room code + join URL |
| `<LiveQuestion />` | `event`, `room`, `base`, `showResults` | Active question, rich media prompt, live results |
| `<LiveQa />` | `event`, `room`, `base`, `limit`, `title` | Top upvoted approved audience questions |
| `<LiveQr />` | `event`, `room`, `base`, `results` | Back-compat card combining join + question |
| `<PresenterPanel />` | `event`, `room`, `base`, `open`, `hotkey`, `fab` | Presenter overlay: author and drive questions |
| `<Podium />` | `event`, `room`, `base`, `limit`, `title` | Quiz podium: top three scorers |
| `<Leaderboard />` | `event`, `room`, `base`, `limit`, `title` | Top participants by quiz points |
| `<LiveReactions />` | `event`, `room`, `base` | Floating emoji from the audience |

Drop them into any slide:

```md
---
layout: center
---

# Ask me anything

<LiveJoin />

<div class="mt-8">
  <LiveQuestion />
</div>
```

!!! tip "Component props are optional"
    Point a component at a room with a prop (`room="AB2C3"` or
    `event="my-event-code"`), or leave it empty and set the build-time
    variables below. `<LiveJoin :size="200" :hint="false" />` shrinks the QR
    and hides the join hint.

## Room and base resolution

Address resolution, most specific first:

1. **Prop** — `room="AB2C3"` (short code) or `event="my-event-code"` (stable code).
2. **Environment** — `VITE_ROOM_CODE` / `VITE_EVENT_CODE` baked in at build time.
3. **Hint** — with nothing configured, components render a visible
   "not configured" hint instead of a broken QR code.

The server URL is the `base` prop, then `VITE_LIVE_BASE_URL`, then same-origin
(the all-in-one container). A short room code is resolved to the event at
runtime via `GET /api/join/{room}`.

```bash
VITE_ROOM_CODE=AB2C3 npm run build -w meetup          # resolve a short room code
VITE_EVENT_CODE=my-event-code npm run build -w meetup # stable event code
VITE_LIVE_BASE_URL=https://meetup.example.com npm run build -w meetup # hosted backend
VITE_STATIC_EXPORT=1 npm run build -w meetup          # presentation-only, hide live UI
```

!!! note "Static export"
    `VITE_STATIC_EXPORT` marks a deck as presentation-only: the presenter panel
    and reactions are hidden entirely, and components that need a room render
    nothing when unconfigured. The GitHub Pages workflow sets it automatically
    when no `LIVE_BASE_URL` is configured — see [Deployment](deployment.md).

## Interactive slides (markdown layouts)

Instead of (or alongside) dropping components into slides, a deck author can
turn a slide into a live question by setting one of the bundled **layouts** in
the slide frontmatter. The layout renders the prompt and the live question via
the shared `useDeckSlideQuestion` composable — no second WebSocket, and no
`onMounted` self-activation from viewers.

`decks/meetup/layouts/` and `templates/deck/layouts/` ship these layouts:

| Layout | Frontmatter `layout` | Renders |
| --- | --- | --- |
| `poll.vue` | `poll` | Single-choice poll |
| `multi.vue` | `multi` | Multi-select |
| `ranking.vue` | `ranking` | Ranked order |
| `yesno.vue` | `yesno` | Yes / No |
| `rating.vue` | `rating` | 1–5 stars |
| `nps.vue` | `nps` | 0–10 |
| `open.vue` | `open` | Open text |
| `wordcloud.vue` | `wordcloud` | Live word cloud |
| `qa.vue` | `qa` | Q&A board (`LiveQa`) |
| `grid2x2.vue` | `grid2x2` | 2×2 scatter/quadrant board |

### Layout frontmatter

Each interactive slide declares a **stable** `id` (never a slide index) and its
prompt. The `kind` is inferred from the layout name unless you set it
explicitly:

```md
---
layout: poll
interactive: true
id: s03-poll-cicd         # REQUIRED stable slug — never use the slide index
prompt: "Where are you on your cloud-native journey?"
options: ["Exploring", "Running in prod", "Scaling platform"]
kind: poll                # optional explicit kind (else inferred from layout)
points: 100               # -> points_base
correct: 1                # 0-based index, for poll | yesno
timeLimit: 30             # seconds, 0 = untimed
duration: 60              # auto-close after N seconds (host auto-reveal respected)
activate: auto            # auto (default) | manual — manual skips auto-activation
showResults: true         # whether the audience sees the live tally
---

<!-- grid2x2 only: -->
---
layout: grid2x2
interactive: true
id: s09-grid-priorities
prompt: "Where do you place each topic?"
axes:
  x: { label: "Impact", low: "Low", high: "High" }
  y: { label: "Effort", low: "Low", high: "High" }
---
```

| Field | Maps to | Notes |
| --- | --- | --- |
| `id` | `slide_id` / `external_id` | Required, stable; upsert key (`{deck_slug}:{id}`) |
| `interactive` | — | `true` (or a known interactive `layout`) marks the slide for sync |
| `prompt` | `prompt` | Falls back to `title`; required to be synced as a question |
| `options` | `options` | Needed for `poll`/`multi`/`ranking` |
| `kind` | `kind` | Optional; inferred from `layout` |
| `points` | `points_base` | Default `100` |
| `correct` | `correct_index` | 0-based index, or omit for a non-scored prompt |
| `timeLimit` | `time_limit_s` | `0` = untimed |
| `duration` | `duration_sec` | Auto-close timer |
| `activate` | `auto_activate` | `auto` (default) or `manual` |
| `showResults` | `show_results` | Default `true` |
| `axes` | — | Read by the `grid2x2` layout for its axis labels; not stored |

The `qa` layout renders the Q&A board and is not itself a question, so it has no
`prompt` and is not part of the slide sync.

Changing a slide's position keeps votes because the `id` is the key. Removing a
slide from markdown archives its row (`status='closed'`) rather than deleting it
on the next sync.

### Automatic activation on slide change

Activation is **server-side**, driven by the presenter's slide broadcast:

1. The presenter's browser sends `{type:"slide", index, total, title, id}` over
   the audience WebSocket on every slide change (see the presenter panel and
   `global-top.vue`).
2. The server maps the slide `id` to `external_id = "{deck_slug}:{slide_id}"`
   (or, without a `deck_slug`, the most recently created question with that
   `slide_id`).
3. If that question is still a `draft` and `activate` is not `manual`, the
   server activates it and broadcasts the new state. Viewers and audience
   phones never self-activate.
4. Setting `activate: manual` still broadcasts the slide (so the projector
   follows) but leaves activation to the host's **Reveal** / **Close** buttons.

The presenter's slide is also cached and pushed to the projector and audience
app, and a **remote deck navigation** control in `/admin` drives the same
channel so the host can step the deck from the admin panel.

### Optional dev-time sync

To iterate against a running backend, sync a deck's interactive slides without a
full deploy:

```bash
DECK_SYNC_BASE_URL=http://localhost:6270 \
DECK_SYNC_EVENT_ID=1 \
DECK_SYNC_TOKEN=<admin bearer or session cookie> \
DECK_SLUG=meetup \
npm run sync:deck -w meetup

# preview the payload without posting:
npm run sync:deck:dry -w meetup
# or: SLIDES_PATH=./slides.md node scripts/sync-deck.mjs --dry-run
```

`scripts/sync-deck.mjs` parses the deck frontmatter and `POST`s
`{ deck_slug, slides: [...] }` to
`POST /api/admin/events/{id}/deck/sync`. The server upserts each slide keyed by
`external_id`, resets it to `draft`, and closes (archives) any previously synced
slide that is no longer present. It is a no-op when `BASE_URL` / `EVENT_ID` are
unset, so a plain `slidev build` never fails.

In dev the optional Vite plugin `plugins/deck-sync.ts` watches `slides.md` and
debounces the same sync on every save. It is a no-op unless the sync env vars
are set.

!!! note "Which path do I need?"
    On the all-in-one container, **markdown comment-block questions** are
    imported from the build manifest at startup (see below). Interactive
    **layout** questions are not part of that manifest — sync them once with
    `npm run sync:deck` (or let the dev plugin do it while you edit).

## Authoring questions in markdown

A deck author can also declare questions **inline in `slides.md`** with an HTML
comment block. It renders nothing in the slides, and any slide can hold one:

```md
<!-- live-question
id: k8s-control-plane
kind: multi
prompt: Which of these are Kubernetes control-plane components?
options:
  - kube-apiserver
  - etcd
  - kubelet
  correct: 0
points: 100
time_limit_s: 30
-->
```

The block is a YAML object between `<!-- live-question` and `-->`. It is parsed
at build time, so the questions travel with the deck.

### Fields

| Field | Required | Default | Notes |
| --- | --- | --- | --- |
| `id` | no | slug of `prompt` | Upsert key; auto-generated when omitted, de-duplicated with `-2`, `-3`, … |
| `kind` | no | `poll` | One of `poll`, `multi`, `ranking`, `yesno`, `rating`, `nps`, `open`, `wordcloud`; an unknown kind falls back to `poll` (`grid2x2` is layout-only) |
| `prompt` | yes | — | The question text; blocks without a prompt are skipped |
| `options` | for `poll`/`multi`/`ranking` | — | `poll`/`multi`/`ranking` need ≥ 2; ignored for other kinds |
| `correct` | no | omitted | Correct answer as a 0-based index **or** exact option text (case-insensitive). Omit for a non-scored prompt |
| `points` | no | `100` | Maps to `points_base` |
| `mode` | no | `live` | `live` or `feedback` |
| `show_results` | no | `true` | Show the live tally |
| `time_limit_s` | no | `0` | Answer lock deadline in seconds |
| `duration_sec` | no | `0` | Auto-close timer in seconds |
| `media_url` / `media_type` | no | empty | Optional image/video prompt |

### Scored vs non-scored

- **Scored** (`correct` set) — behaves like a quiz question: points are awarded
  on submission (speed-scaled), disclosed at reveal, and the leaderboard counts
  them.
- **Non-scored** (`correct` omitted) — a poll-style interaction prompt: the live
  result bars render, but **no points** are awarded, there is no correct answer
  and no pass/fail, `is_correct` stays `NULL`, and the leaderboard is
  unaffected.

### Build manifest and startup seeding

`npm run build` runs `scripts/extract-questions.mjs` after building the decks.
It discovers every built deck (`dist/<deck>/index.html`), parses the
`<!-- live-question -->` blocks from that deck's `slides.md`, and writes
`dist/<deck>/questions.json`:

```json
{
  "deck": "feature-test",
  "event_code": "feature-test",
  "event_name": "Live feature test deck",
  "questions": [
    {
      "id": "stack-favourite",
      "kind": "poll",
      "mode": "live",
      "prompt": "Which part of the stack do you want to dig into next?",
      "options": ["Kubernetes", "GitOps and CI/CD"],
      "correct_index": null,
      "points_base": 100,
      "show_results": true,
      "time_limit_s": 0,
      "duration_sec": 0,
      "media_url": "",
      "media_type": "",
      "slide_index": 3
    }
  ]
}
```

When `SEED_DECK_QUESTIONS` is truthy (the published image sets it to `1`), the
server walks `DECKS_DIR` on startup, reads every `questions.json`, and seeds the
questions into the event whose `code` equals the manifest's `event_code`
(falling back to the deck directory name). Missing events are created.

Seeding is **idempotent by question `id`** (stored in `questions.seed_key`):
re-importing updates the existing row in place rather than duplicating it, and
the markdown stays the **source of truth** — edits to `slides.md` are applied on
the next container start / upgrade.

Each question also carries `slide_index` — the 1-based Slidev slide that
contains its `<!-- live-question -->` block. Seeding stores it as the deck
mapping (`external_id`, `deck_slug`, `slide_id`, with `auto_activate` enabled),
and the deck's `questions.json` lets the presenter panel translate the current
slide into that question's id. When the presenter lands on the slide, the deck
broadcasts the id and the server opens the question for the audience, so a
QR-joined participant sees and can answer the multi-choice question in sync
with the presented slide.

!!! tip "Feature-test event"
    With `SEED_FEATURE_TEST` truthy (also set to `1` in the published image) the
    server creates a deterministic `feature-test` event on startup so the
    bundled `feature-test` deck auto-connects with no query params. The
    `feature-test` deck bakes in `VITE_EVENT_CODE=feature-test` and resolves the
    API same-origin; `?event=<code>` still overrides.

### Offline and static fallback

Markdown comment-block questions ship inside the built deck, so a deck that
never reaches a backend still builds and presents normally. Live components
without a configured room render the join card and wait; interactive layouts
show a "No room set" / "Waiting" pill until a question is active.

## Presenter panel

`<PresenterPanel />` turns the deck itself into the presenter console, so you
can **ask and close live questions without leaving the slides**.

1. Add the component once per deck (it renders as an overlay, not a slide):

   ```md
   <PresenterPanel room="AB2C3" fab />
   ```

2. Open it with the `p` hotkey, the corner ▶ button (`fab`), or pin it on a
   presenter-only slide with `<PresenterPanel :open="true" />`.
3. Sign in with a local admin account, or reuse the admin session already active
   in the same-origin container (including one created through OIDC login).
4. Pick the **kind** — poll, multi-select, ranking, yes/no, rating, NPS, open
   text or word cloud — write the prompt, and for the choice kinds add
   comma-separated options.
5. Optionally attach an **image or video** to the prompt (upload a file or paste
   a URL); the audience sees it with the question.
6. **Ask now** pushes the question live to every audience device, **Save draft**
   stores it for later, **Reveal** publishes the correct answer and results, and
   **Close current** ends the active question.
7. **Show podium** swaps the projector and audience screens to the quiz
   leaderboard; asking the next question hides it again.

| Panel option | Default | Effect |
| --- | --- | --- |
| `hotkey` | `p` | Key that toggles the panel |
| `open` | `false` | Start with the panel open (good on a presenter slide) |
| `fab` | `false` | Show a small corner ▶ button |
| `event` / `room` / `base` | `""` | Address resolution, as above |

The panel header shows the resolved room and the live answer count. In the
all-in-one container this is same-origin and uses the admin session cookie. On
GitHub Pages the deck is cross-origin, so the backend must allowlist the Pages
origin — set `CORS_ORIGINS`. See [Configuration](configuration.md).

### Panel fields

When authoring a question the presenter panel offers:

| Field | Notes |
| --- | --- |
| Kind | `poll`, `multi`, `ranking`, `yesno`, `rating`, `nps`, `open`, `wordcloud` |
| Show results | Whether the audience tally is shown (legacy instant feedback) |
| Feedback | Route the question to the post-event feedback form |
| Timer | `Untimed`, `5s` … `180s` — the auto-close duration |
| Auto-reveal | Publish the correct answer and results when the timer expires |
| Prompt | The question text |
| Options | Comma-separated, for choice kinds |
| Time limit | `time_limit_s`, `0` = untimed (locks answers on expiry) |
| Media | Upload an image/video or paste a URL |
| Quiz scoring | Correct answer + base points (poll / yes/no only) |

!!! tip "Speed bonus"
    Scored answers award up to the base points, scaled by how fast the
    participant answered. Points are scored on submission but only disclosed at
    reveal.

## Quiz game loop

Scored poll and yes/no questions can run as a timed round. Set a **time limit**
in the presenter panel (or `time_limit_s` through the API) and the audience and
projector count down to a server-computed deadline that survives reconnects.

When time runs out the question **locks**: answers are rejected and results stay
hidden. The host then **reveals** the correct answer (presenter panel or admin
console), which also publishes the tally and each participant's result.

```
draft ──activate──▶ live ──timeout──▶ locked ──reveal──▶ revealed
                     │                                     ▲
                     └───────────── reveal ────────────────┘
                     └───────────── close ─────────────▶ closed
```

- Points are scored on submission but only disclosed at reveal — unless
  `show results` is on, which keeps the legacy instant feedback.
- **Show podium** puts the top three scorers on the projector and audience app;
  activating any question clears it.

See [Questions](questions.md) for the scoring formula and per-kind behavior.

## Audience questions (Q&A)

Audience members ask from their phones, not from the deck: scan the
`<LiveJoin />` QR (or open the join page and enter the room code), switch to the
**Q&A** tab, and submit a question with an optional name.

The backend queues it for moderation; an admin approves, hides or marks it
answered in `/admin`. Approved questions can be upvoted, `<LiveQa :limit="5" />`
mirrors the top-voted ones on a slide, and `<LiveQuestion />` shows the active
prompt with its live results.

See [Moderation & safety](moderation.md) for the content filter, the answer
moderation queue and Q&A slow mode.

## Reactions and identity

- Participants pick a display identity (name, emoji, colour) per event.
- `<LiveReactions />` renders floating emoji sent from the audience app.
- `<Leaderboard />` and `<Podium />` read the same quiz points.

## Cross-origin decks

When the deck is served from a different origin than the backend (for example
GitHub Pages pointing at a hosted backend), the backend must allowlist the deck
origin and allow the presenter's session cookie cross-site:

```bash
CORS_ORIGINS=https://yourname.github.io
COOKIE_SAMESITE=none
COOKIE_SECURE=true
```

Without an allowlisted origin the presenter cannot sign in from the deck. See
[Configuration](configuration.md).

## Theming

The interactive layouts do **not** ship a custom Slidev theme — they sit on top
of the default theme and only style the centred live card. The panel palette,
radii and typography come from CSS custom properties (`--accent`, `--grad`,
`--surface`, `--border`, `--text`, `--muted`, `--font-display`, `--font-mono`,
`--radius-card`) defined in each deck's `style.css` (and, in the template,
`styles/index.css`).

`THEME.md` (in both `decks/meetup/` and `templates/deck/`) documents the
authoring contract: the interactive layouts, the frontmatter fields above, the
`external_id` key, and the sync/activation flow. `templates/deck/**` is the
canonical copy; `decks/meetup/**` mirrors it, so edits are applied to both.
